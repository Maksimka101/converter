## Суть
Парсер и вычислитель выражений на чистом Kotlin, отделённые от UI, чтобы их было легко тестировать и расширять.

## Обсуждение / варианты
- Интерфейс под каждый язык отклонён: грамматика у языков общая, отличаются только слова.
  Интерфейс понадобился бы языку с другим порядком слов или морфологией, которую нельзя перечислить.
- Вычисление прямо в парсере, без AST, отклонено: дерево удобно проверять в тестах и пересчитывать
  при обновлении курсов без повторного разбора.
- Балансировка скобок внутри парсера отклонена: парсер усложняется, позиции для хинта достать труднее.
- Балансировка после построения AST невозможна: от виртуальных скобок зависит сама форма дерева
  (`10-2)*3+1)`).
- Pratt-парсер вместо recursive descent — дело вкуса, не меняли.
- Отдельный Gradle-модуль `parser` отклонён 2026-09-24 (#2): хватает пакета.
- Этапы как функции вообще без интерфейсов отклонены 2026-09-24: нужна явная граница, которую
  пользователь проверяет сам.

## Решение
Принято 2026-09-22, конвейер — 2026-09-23, гейт — 2026-09-24.
- Парсер пишем **свой**, готовые библиотеки не берём — семантика слишком своя (валюты, проценты,
  виртуальные скобки), чужой парсер пришлось бы переделывать больше, чем написать с нуля.
- Пакет `calc` — чистый Kotlin, без `android.*`; тесты гоняются на JVM без эмулятора.
- **Гейты** — интерфейсы этапов и публичные модели с пометкой `ГЕЙТ` (правило в `CLAUDE.md`).
  Код: `calc/Calculator.kt`, `calc/Calculation.kt`, `calc/engine/Stages.kt`, `core/Rates.kt`.
- Этап, который не может продолжить, бросает `Stop(outcome)`; `Calculator` превращает его
  в результат. Так recursive descent не тащит результат через каждый вызов.

### Конвейер
```
text → Lexer(lexicon) → tokens → Balancer → tokens → Parser → Node → eval(node, rates) → Value
```
- Этапы внутри `calc.engine`. AST — `sealed`-иерархия, `eval` — одна функция с `when`.
- **Лексер**: текст → токены со `span`. Словарь `Lexicon` (слово → токен) — данные, а не код.
  RU и EN сливаются в один словарь, язык интерфейса на разбор не влияет (#5). Склонения — перечисленные
  формы, без стеммера. При сборке словаря проверяем, что слова разных языков не конфликтуют.
- **Слово** — максимальная серия букв (плюс `$` для `C$`, `US$`), совпадает со словарём целиком.
  Поэтому `в` не пересекается с `вон`, `10 mxn` — песо, а не 10 млн, а `15круб` — ошибка.
- **Балансировщик** вставляет синтетические `(`/`)` по правилам #5. Синтетический токен нулевой ширины
  и знает позицию в тексте, позиции виртуальных `(` уходят в UI для хинта. Балансировщик держит
  маленькую таблицу классов токенов: начало операнда, инфиксный, постфиксный.
- **Парсер** — recursive descent без отката, скобки в нём всегда парные.
- **eval(node, rates)** — типы и правила #5. Топ-N (#8) конвертирует итоговое значение, дерево заново
  не вычисляется.
- Под домашнюю валюту (идея в #8) в конвейере ничего не закладываем.

### Результат и ошибки
Модели — `calc/Calculation.kt` (`Calculation`, `Value`, `CalcError`, `Span`), токены и дерево —
`calc/engine/Syntax.kt`.
- `span` есть у каждого токена и узла. Узел покрывает своих детей, узел неявного умножения — оба операнда.
- Ошибка — это `CalcError` и `span`, данные есть только там, где их не вынуть из текста
  (`kr` → варианты). Текст сообщения живёт в ресурсах, в `calc` строк UI нет.
  UI подчёркивает `span` той же `VisualTransformation`, что рисует хинт виртуальной `(`.
- Отдаём только первую ошибку, восстановления после ошибки нет.
- Кто что ловит: лексер — неизвестное или неоднозначное слово (`span` слова); парсер — неожиданный
  токен (`span` токена); eval — ошибки типов, деление на ноль, нет курса (`span` узла).

### Incomplete
- **Incomplete — ввод, который можно дописать справа до валидного.** Если чинить надо в середине — Error.
- Парсер: recursive descent без отката падает на первом токене, после которого валидного продолжения нет.
  Упал на EOF или на синтетической `)` из R2 в конце (#5) → Incomplete, раньше → Error.
  `5 +`, `5 + (`, `5 usd *`, `10 usd to` → Incomplete; `5 5` → Error на второй `5`.
- Лексер: слово вплотную к концу текста — однозначное точное совпадение даёт токен, префикс слова из
  словаря дают Incomplete; неоднозначное слово — Incomplete, только если его можно дописать до другого слова
  словаря (`kr` → `krw`), иначе Error (`10 песо`); остальное — Error. Пробел заканчивает слово:
  `10 us` → Incomplete, `10 us ` и `10 kr + 5` → Error, `10 k` = 10000.
- Незаконченная группа разрядов в конце (`1 0`, `1 00`) → Incomplete (правило группировки в #5).
- eval работает с полным деревом, его ошибки всегда Error.

## Как реализовано
- Этапы: `engine/LexiconLexer.kt` (+ словарь `engine/Lexicon.kt`, #5), `engine/BracketBalancer.kt`,
  `engine/RecursiveDescentParser.kt`, `engine/TypedEvaluator.kt`; склейка и `defaultCalculator()` — `calc/PipelineCalculator.kt`.
  Тесты: JUnit 4 на JVM (`testImplementation(libs.junit)`), по файлу на этап + сквозной `PipelineCalculatorTest`.
- Лексер: `1 0` и `1 00` в конце — Incomplete только для группы из одних нулей (иначе `5 5` было бы Incomplete,
  а это два числа); для `_` и `'` — любые 1–2 цифры. `10.` в конце — Incomplete, в середине — BadNumber. `.5` без
  ведущей цифры не поддерживается. Точка после валютного или множительного слова съедается (`тыс.`, `руб.`).
- Балансировщик: валюта сразу после синтетической `)` — суффикс группы и остаётся снаружи, как `%`. Непарная `)`
  (`10 + ) 5)`) — барьер: следующий сегмент начинается после неё, виртуальные `(` через неё не спариваются.
- Парсер: знак у `$-10` считается знаковым, только если вплотную к валюте и числу и это `-`; `usd - 5` и `$+10` — бинарные.
  Span у MissingOperator — весь второй операнд (`5 eur` в `10 usd 5 eur`).
- Вычислитель: Percent ÷ Number сворачивается в число (в #5 есть только P ÷ P → N), поэтому `100 usd + 10% / 2` —
  MixedNumberMoney. Кросс-курс `rate(a, b)` в DECIMAL128 неточный: `10 usd + 9 eur` = 19.999…9, ровно 20 даст только
  округление при выводе (#5).
