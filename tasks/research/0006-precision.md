# Исследование к задаче #6: представление чисел и точность

Здесь только варианты с плюсами и минусами. Решение записывается в `tasks/0006-precision.md`.

## Требования
- Точность до цента или копейки у фиата. Крипта: BTC 8 знаков, у части токенов 18 (wei).
- Крошечные значения: 1 USD ≈ 0.0000xx BTC, цена SHIB ≈ 0.00001 USD.
- Цепочки вроде `100 / 3`, `10 usd - 10%`, кросс-курс EUR→JPY через USD.
- Логика на чистом Kotlin без `android.*`, мало зависимостей, в будущем возможен KMP.

## Варианты

### 1. Два инта: целая и дробная часть (идея пользователя)
Число хранится как `(int, frac)`, где `frac` означает число единиц `10^-scale`.
- **Масштаб всё равно фиксированный.** `frac = 5` может значить 0.5 или 0.05, поэтому нужен
  общий `scale`. При 2 знаках BTC не влезает. При 8 знаках SHIB (0.00001) хранится всего с 3 значащими
  цифрами. 18 знаков не влезают в `Int` (максимум ≈ 2.1·10^9, то есть 9 знаков).
- **Знак.** Как хранить −0.5? Знак у `int = 0` теряется, поэтому нужен отдельный флаг или
  договорённость «знак у обеих частей». Отсюда много краевых случаев.
- **Перенос.** Сложение: `frac` переполняется за `10^scale`, приходится переносить единицу в `int`,
  а при вычитании занимать её оттуда.
- **Умножение:** `(a + b·10^-s)(c + d·10^-s)` даёт четыре перекрёстных слагаемых, `b·d` имеет масштаб
  `2s` и требует округления. Каждое произведение может переполнить `Int`.
- **Деление** напрямую не делается. Пришлось бы собрать число обратно в одно целое `a·10^s + b`
  и поделить его, то есть это вариант 2, только с лишними шагами.
- Переполнение: целая часть ограничена ≈ 2.1 млрд. Это мало для `1 btc to idr` или `1e9 * 3`.
- Итог: по сути это Long в минимальных единицах (вариант 2), разрезанный на две части. Сложность
  выше, выигрыша нет. Зависимостей нет, KMP-совместимо.

### 2. Long в минимальных единицах или с фиксированным масштабом
`value: Long` с общим `SCALE` (например 10^8) или с масштабом по валюте (центы, сатоши).
- Сложение и вычитание точные и быстрые, код простой, зависимостей нет, KMP без проблем.
- **Переполнение:** `Long.MAX ≈ 9.22·10^18`. При масштабе 8 это ≈ 92 млрд единиц, терпимо.
  При масштабе 18 остаётся ≈ 9.2 единицы, то есть ничего. Умножение двух чисел со скейлом `s` даёт
  промежуточный масштаб `2s`: при s=8 сырое `a*b` переполняется уже на `31 * 31`
  (3.1·10^9 × 3.1·10^9 > 9.2·10^18). Нужны `Math.multiplyHigh` и ручной 128-битный код.
- **Деление и округление** надо писать вручную: `100/3` при s=8 даёт 33.33333333, остаток теряется,
  режим округления реализуем сами.
- Курсы плохо ложатся в этот формат: `0.00000923` при s=8 даёт 923, всего 3 значащие цифры,
  и ошибка переходит в результат. Кросс-курс = деление, та же проблема.
- Подходит для бухгалтерии в одной валюте, плохо подходит для калькулятора с произвольными курсами.

### 3. `java.math.BigDecimal`
Число хранится как `unscaledValue: BigInteger` и `scale: Int`, то есть это десятичная дробь
произвольной точности.
- **Точность:** `+ − ×` и проценты точные. `0.1 + 0.2 = 0.3`. Длина мантиссы не ограничена,
  18 знаков и SHIB не проблема.
- **Переполнения нет** (в пределах памяти).
- **Деление:** `100/3` без контекста бросает `ArithmeticException` (бесконечная дробь). Нужен
  `MathContext`, например `DECIMAL128` (34 значащие цифры, HALF_EVEN).
  Тогда `100/3*3 = 99.999…9` (34 девятки), и после округления при выводе получается `100`.
- Подводные камни: `equals` учитывает scale (`2.0 != 2.00`), сравнивать надо через `compareTo`.
  Нельзя создавать из Double (`BigDecimal(0.1)` даёт 0.1000000000000000055…), только из строки.
- Сложность низкая: всё уже реализовано. Внешних зависимостей нет, есть в JDK и на Android с API 1.
- **Портируемость:** работает только на JVM (Android, desktop). Для KMP есть
  `com.ionspin.kotlin:bignum` (чистый Kotlin, `BigDecimal` и `BigInteger`, JVM/JS/Native/Wasm).
  Если спрятать тип за своей обёрткой, переезд сводится к замене реализации.
- Скорость: для калькулятора с парой десятков операций на ввод несущественна.

```kotlin
val MC = MathContext.DECIMAL128
@JvmInline value class Num(val v: BigDecimal) {
    operator fun plus(o: Num) = Num(v.add(o.v))
    operator fun times(o: Num) = Num(v.multiply(o.v))
    operator fun div(o: Num) = Num(v.divide(o.v, MC))       // 100/3 не бросает
    fun percentOf(p: Num) = Num(v.multiply(p.v).divide(BigDecimal(100)))  // точное
    companion object { fun parse(s: String) = Num(BigDecimal(s)) }  // только из строки
}
```

### 4. Double с округлением только при выводе
- Около 15–17 значащих цифр, диапазон огромный, переполнения на практике нет, KMP есть везде,
  код самый короткий.
- **Почему опасно для денег:** двоичная дробь не хранит `0.1` точно. `0.1 + 0.2 = 0.30000000000000004`,
  `1.005` на самом деле 1.00499999…, поэтому HALF_UP до 2 знаков даёт `1.00`, а не `1.01`.
  Ошибки копятся в цепочках, при сравнении `==` результаты расходятся, а при выводе «сырого»
  результата пользователь видит мусор вроде `...0000004`.
- Сумма `10^18` wei плюс 1 wei теряет младший разряд, потому что 17 цифр мало.
- **Когда допустимо:** оценочные конвертации, где курс сам по себе приблизителен (6–8 значащих цифр).
  Округление при выводе до 2–8 знаков почти всегда скрывает ошибку. Графики и сортировка тоже.
  Для «точно до копейки» на граничных `.xx5` не годится.

### 5. Рациональные числа (BigInteger числитель и знаменатель)
- **Точность:** `+ − × ÷` точные всегда. `100/3*3 = 100` ровно, без контекста деления.
  Десятичный ввод `0.0000092` точно становится `92/10^7`.
- Переполнения нет. Цена этого: знаменатели растут в длинных цепочках, нужен `gcd` после каждой
  операции. Для калькулятора это приемлемо.
- Округление только одно, при выводе (деление числителя на знаменатель с нужным режимом).
- Минусы: своя реализация на ~150–250 строк (нормализация, знак, gcd, парсинг, форматирование,
  проценты), а также тесты. Не работают дробные степени и корни, если они понадобятся.
- Зависимости: `java.math.BigInteger` на JVM или ionspin `BigInteger` для KMP.

## Когда и как округлять
- **Только при выводе.** Промежуточные значения держать в полной точности. Единственное
  вынужденное место: деление в BigDecimal с контекстом 34 цифры, это на порядки точнее вывода.
  Округлять на каждом шаге нельзя: `10 usd / 3 * 3` станет 9.99.
- **Режим:**
  - HALF_EVEN (банковский, по умолчанию в IEEE и DECIMAL128) не даёт систематического сдвига при
    суммировании многих округлённых значений.
  - HALF_UP соответствует школьному правилу (`2.5 → 3`). Пользователь проверяет в уме именно так.
  - Здесь округление однократное, при показе, накопления нет, поэтому смещение HALF_EVEN не нужно.
  - Разумная схема: HALF_EVEN внутри деления, HALF_UP при выводе.
- **Знаки по валюте:** своя таблица по ISO 4217 (JPY, KRW 0; большинство фиата 2; KWD, BHD 3;
  BTC 8; ETH до 18, но показывать не больше 8). `java.util.Currency.defaultFractionDigits`
  работает только на JVM и крипту не знает, поэтому лучше своя таблица.
- **Мелкие значения:** если после округления до знаков валюты получается 0, а число не 0,
  показывать N значащих цифр (например 4): `0.00001234 usd`, `0.00001523 btc`.
  Для числа вне валюты (`100/3`) показывать до ~10 знаков и отрезать хвостовые нули.

```kotlin
fun display(x: BigDecimal, decimals: Int, sig: Int = 4): BigDecimal {
    val r = x.setScale(decimals, RoundingMode.HALF_UP)
    return if (r.signum() == 0 && x.signum() != 0)
        x.round(MathContext(sig, RoundingMode.HALF_UP)) else r
}
```

## Точность самих курсов
- API отдаёт курсы с 6–10 значащими цифрами (`0.0000092341`). Точность результата ограничена
  курсом. Выводить 12 знаков при курсе с 6 значащими означает показывать ложную точность.
- Парсить курс из JSON **строкой** прямо в десятичный тип, не через Double
  (`JsonPrimitive.content` в kotlinx.serialization). Иначе погрешность Double попадёт в данные.
- Кросс-курс EUR→JPY через базу USD: `amount * rate[JPY] / rate[EUR]`. Сначала умножать, делить
  один раз в конце. Кросс-курс заранее не округлять и не кэшировать округлённым.
- Хранить курсы как строки или BigDecimal (в кэше и моках из #15), а не Double.

## Рекомендация (не решение, выбор за пользователем)
**BigDecimal за собственной обёрткой `Num` в core-модуле**, деление с `MathContext.DECIMAL128`,
курсы парсятся из строк, округление HALF_UP только при выводе по таблице знаков валюты с запасным
вариантом на значащие цифры.
- Почему: точная десятичная арифметика без своего кода, нет переполнений, 18 знаков и SHIB без
  проблем, внешних зависимостей нет. Обёртка оставляет путь в KMP через ionspin bignum.
- Идею «2 инта» не рекомендую: это Long с фиксированным масштабом, только сложнее, а у Long
  масштаб и переполнение не подходят под крипту.
- Рациональные числа стоит держать в уме, если захочется точного `100/3*3 = 100` без хвоста
  (при выводе BigDecimal и так покажет 100). Double подходит только как осознанное упрощение
  для «примерного» конвертера.
