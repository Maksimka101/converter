# Исследование: frecency валют (#8)

Связано: #9 (топ-N), #12 (история), #16 (список и закрепление), #10 (неполный ввод).
Здесь только варианты. Решение принимает пользователь, рекомендация помечена **[Рекомендация]**.

## 1. Когда засчитывать использование

### A. Каждое добавление токена валюты (предложение пользователя)
Плюсы: просто, реагирует сразу, не нужен явный «конец» выражения.
Проблемы:
- **Недонабранные токены.** `e` → `eu` → `eur`: при живом парсинге на каждом шаге есть «валюта».
  `r` может совпасть с `rub`, префикс `u` подходит к `usd/uah/uzs`. Засчитывать нужно только
  точное распознавание, а не догадку автодополнения (#18). Даже при точном совпадении промежуточные
  состояния бывают реальными кодами: при правке `cup` → `cu` → `cuc` засчитается и CUP, и CUC.
- **Правки и backspace.** `10 eur` → стёр → `10 eu` → `10 eur`: одно намерение, два засчитывания.
- **Повтор того же выражения** (пересчитал, вернулся из истории): засчитывать ли снова? Скорее да, это реальное использование.
- **Одна валюта дважды** (`10 usd + 5 usd to eur`): должна считаться один раз на выражение.
- Итог: чистый вариант A «засоряет» статистику пропорционально числу правок, а не числу использований.

### B. Засчитывать зафиксированный токен
Токен считается зафиксированным, если за ним следует пробел/оператор/`to`, либо разбор выражения
стабилен N секунд (debounce 1.5–3 с). Внутри одного выражения валюта считается один раз (Set).
Плюсы: отсекает большинство промежуточных состояний, всё ещё «живой».
Минусы: backspace после пробела всё равно даёт повторы (лечится Set-ом на выражение);
debounce зависит от темпа пользователя; нужен «идентификатор выражения» (когда начинается новое?).

### C. Один раз на «сессию выражения» по завершению
Засчитывать множество валют итогового выражения при копировании, выходе из приложения, очистке поля
или паузе (≥ N с без правок). Это тот же триггер, что и запись в историю (#12).
Плюсы: одно выражение = одно использование, промежуточный мусор исключён полностью, совпадает с историей.
Минусы: при убийстве процесса событие может потеряться (сохранять на `onStop`); пауза требует таймера.

### D. Только действия с результатом (#11: копирование, шаринг)
Плюсы: самый «честный» сигнал ценности. Минусы: многие лишь смотрят результат, не копируя;
статистика будет скудной, холодный старт затянется.

### E. Гибриды
- C + вес: действие с результатом (копирование) даёт больше очков, чем просто завершённое выражение.
- B внутри выражения (для подсказок в реальном времени) + C для записи в хранилище.

### Источник vs цель
- `10 usd to eur`: оба важны. Цель явно выбрана (`to` пишут, когда нужной валюты нет в топе),
  это сильный сигнал «нужна в топе». Источник отражает, какие деньги у пользователя.
- Варианты: равный вес (просто); цель ×1.5–2 (быстрее попадает в топ-N, и `to eur` больше не нужен, цель #9).
- Показанные в топ-N валюты **не засчитывать** за просмотр: иначе положительная обратная связь
  (в топе → засчитали → остаётся в топе), новые валюты никогда не пробьются.
  Исключение: копирование конкретной строки топа (#11) засчитывает её валюту как цель.

**[Рекомендация]** C + E: засчитывать множество различных валют итогового выражения один раз при
завершении (копирование / очистка / выход / пауза ~3 с), источник вес 1, явная цель `to` вес 1.5,
копирование строки топа — вес 1 этой валюте. Просмотр не засчитывать. Триггер общий с историей (#12).

## 2. Формула

| Вариант | Суть | Хранение | Плюсы | Минусы |
|---|---|---|---|---|
| Firefox-корзины | каждое посещение весит по возрасту: <4 дн 100, <14 дн 70, <31 дн 50, <90 дн 30, иначе 10 | список последних ~10 событий на валюту | понятно, проверено | нужны события, ступенчатость |
| Экспоненциальный распад | `score = score·2^(-Δt/T) + w`, T = период полураспада | score + lastUpdated | 2 числа, плавно, ленивый пересчёт | T надо подобрать |
| zoxide | при сумме всех score > max (напр. 10000) все умножаются на 0.9, мелкие удаляются; ранг = score × множитель давности (×4 <1 ч, ×2 <1 дн, ×0.5 <1 нед, иначе ×0.25) | score + lastAccess | ограниченный рост, чистит мусор | два механизма, ступени |
| Только частота / только давность | счётчик или LRU | 1 число | проще всего | частота «залипает», LRU прыгает |

Экспоненциальный распад эквивалентен сумме `w·2^(-age/T)` по всем событиям, т.е. «гладкие корзины».
Хранение: на валюту `score` (Double) и `updatedAt` (epoch ms). Распад применяется лениво: при
чтении и при добавлении. Для сравнения удобно хранить «score, приведённый к эпохе»:
`logScore = ln(score) + t/τ`, тогда сортировка не требует пересчёта — но это оптимизация, валют ~150, не нужна.

Полураспад: 14 дней — быстро подхватывает поездку в другую страну; 30 дней — стабильнее.
**[Рекомендация]** экспоненциальный распад, T = 21 день (константа, подобрать на практике), хранение
score + updatedAt в одном JSON/DataStore-файле, ленивый распад. Валюты со score < 0.05 и не
закреплённые можно удалять из хранилища (как zoxide).

## 3. Стабильность порядка
- **Не переупорядочивать во время ввода.** Порядок топ-N вычисляется один раз и замораживается.
- Варианты момента пересчёта: (а) при старте/возврате в приложение (`onStart`); (б) после каждого
  завершённого выражения (поле очищено); (в) раз в сутки. (а) проще всего и предсказуемо.
- Внутри видимого топа можно сортировать не по score, а стабильно: новая валюта заменяет последнюю
  строку, остальные не двигаются (меньше ломает мышечную память), но хуже отражает реальность.
- **Закреплённые (#16)** занимают фиксированные слоты; оставшиеся N−k слотов заполняются по frecency,
  исключая закреплённые и валюту источника выражения (конвертировать usd в usd бессмысленно).
- **Гистерезис** (опционально): валюта вытесняет другую, только если score больше на 10–20 %.
- **Холодный старт:** (1) дефолт из локали: валюта страны (`Locale`/`Currency.getInstance`, в чистом
  Kotlin передаётся параметром) + USD, EUR, GBP, CNY/JPY; (2) выбор пользователя на первом экране —
  лишний шаг, противоречит мгновенному старту (#13); (3) дефолты как «виртуальные» score (напр. 1.0),
  которые естественно распадаются и вытесняются реальным использованием.
  **[Рекомендация]** (1)+(3): засеять дефолты из локали малым score, связать с домашней валютой (#20).

## 4. Frecency из истории (#12)?
Вариант «вычислять»: при старте пройти по истории и посчитать сумму `w·2^(-age/T)` по валютам.
- Плюсы: один источник правды, нет рассинхрона; можно менять формулу/вес задним числом;
  удаление записи из истории честно уменьшает frecency.
- Минусы: история, вероятно, ограничена (напр. 500 записей) или чистится пользователем — вместе с
  ней обнулится топ; нужен повторный разбор выражений (или хранить в записи множество валют);
  связывает #8 с решениями #12 (что считать записью). Сигналы вне истории (копирование строки топа) теряются.
- Вариант «отдельно»: независимый стор score/updatedAt, обновляемый тем же событием, что пишет историю.
  Плюсы: O(1), переживает очистку истории. Минусы: два хранилища.

**[Рекомендация]** общий триггер, раздельное хранение: запись истории содержит список валют (для
будущего пересчёта), frecency хранится отдельно. Если историю решат не делать — ничего не меняется.

## 5. Набросок на Kotlin (чистый Kotlin, без android.*)
```kotlin
data class Usage(val score: Double, val updatedAt: Long)

class Frecency(
    private val halfLifeMs: Long = 21L * 24 * 3600 * 1000,
    private val data: MutableMap<String, Usage> = mutableMapOf(),
) {
    private fun decayed(u: Usage, now: Long): Double =
        u.score * Math.pow(0.5, (now - u.updatedAt).toDouble() / halfLifeMs)

    /** Вызывается один раз на завершённое выражение. */
    fun record(source: Set<String>, targets: Set<String>, now: Long) {
        val weights = source.associateWith { 1.0 } + targets.associateWith { 1.5 }
        for ((code, w) in weights) {
            val old = data[code]?.let { decayed(it, now) } ?: 0.0
            data[code] = Usage(old + w, now)
        }
    }

    /** Считается на старте и замораживается до следующего. */
    fun top(n: Int, pinned: List<String>, exclude: Set<String>, now: Long): List<String> {
        val rest = data.entries
            .filter { it.key !in pinned && it.key !in exclude }
            .sortedByDescending { decayed(it.value, now) }
            .map { it.key }
        return (pinned + rest).take(n)
    }
}
```
Хранение: `Map<String, Usage>` сериализуется в JSON (kotlinx.serialization или вручную), время
передаётся параметром `now` — функции детерминированы и тестируются без Android.
